# Moss: retrieval and grounding

## What Moss does

Moss is CareLoop's retrieval layer, not its patient database and not its treatment selector. It stores condition-specific, patient-safe knowledge such as inhaler technique, controller versus reliever education, warning signs, and action-plan education. It must not contain patient identifiers, call transcripts, or private clinical history.

There are two uses:

1. **Live-call grounding.** When a patient asks a clinical or educational question, Maya calls the server-side `getCareContext` tool. The bridge queries the condition's Moss index and returns the top snippet for a short spoken answer.
2. **Deep-research grounding.** After the call, the research worker queries the same condition index for up to four snippets. Those snippets are supplied to the LLM as clinic knowledge context while it writes a cited rationale.

Insurance questions do not go to Moss; they go to Stedi. Patient-specific historical data does not go to Moss; it is loaded from Medplum into the research prompt and plan context.

## Index model

Each `ConditionModule` provides:

```ts
{
  moss: {
    indexName: "careloop-asthma-kb",
    corpus: [{ id, text, source }]
  }
}
```

The corpus is indexed with `npm run moss:index`. The Asthma and Depression modules can have separate indexes, so a question is routed using the patient's resolved condition module rather than a global index.

## Live technical path

`src/orchestration/tools.ts` resolves the patient and module, then calls:

```ts
getMossClient({
  indexName: module.moss.indexName,
  corpus: module.moss.corpus
}).retrieve(question, { k: 1 })
```

When configured, `src/integrations/moss.ts` lazily imports `@moss-dev/moss`, creates an SDK client with `MOSS_PROJECT_ID` and `MOSS_PROJECT_KEY`, loads the index once per client, and calls `query(indexName, ..., { topK })`. Results are normalized to `{ text, source, score }`.

Lazy loading matters operationally because Moss has a native binding. The production bridge runs Ubuntu 24.04 (glibc 2.39) so the native module loads successfully. If live retrieval fails, the bridge logs `moss.live.fallback` and uses the condition corpus/mock retrieval; the call should continue.

## How the answer is controlled

The tool description restricts Moss to clinical/education questions. The result includes a source label and is charted as a Communication such as `Patient asked: ... → answered from ...`. Maya is instructed to relay a concise answer and not invent a diagnosis or dose.

Moss retrieval is grounding, not proof. The clinician-facing research artifact includes separate citations generated by the research worker. In production, index governance should include source ownership, review dates, versioning, contraindication review, and audit logs for corpus changes.

## Mock mode

Without Moss credentials, `getMossClient` uses a deterministic keyword scorer over the local corpus. This makes `npm run simulate` runnable offline. Mock retrieval is useful for development only and must be labeled as mock in operational telemetry.
